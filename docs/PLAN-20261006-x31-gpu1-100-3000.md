### P1. Dense Q8 GEMM (largest item, G-X)
SASS of `gemm_kernel` (`cuobjdump -sass`, built from the tree): main loop ~500 instructions per 32 IMMA
(~15 non-tensor instructions per IMMA: 4 I2FP + 4 FMUL + 4 FFMA + addressing/predication), double buffered, KC=64.
That is issue-slot parity with the tensor pipe, so the 25% is stalls and occupancy, not raw instruction count.
Do **not** guess a rewrite. Step order:
1. Standalone microbench `tools/tk-bench/q8_gemm_bench.cu` on the real shapes (M=8192 tokens; N,K in
   {10240x2560, 6144x2560, 2560x6144, 12288x2560, 640x2560, ...}): TOPS and the same checksum as production.
2. Variants measured in the microbench only, each bit-identical to the current output (the fold
   `acc += float(c) * (dw*dx)` keeps its exact op order): (a) KC=128 and 3-stage cp.async, (b) scale tile hoisted
   so `dw*dx` and the half->float scale loads leave the k loop, (c) `I2FP` replaced by the magic-number
   conversion (`__int_as_float(c + 0x4B400000) - 12582912.f`, exact for |c| < 2^22; |c| <= 516,096
   here; prove with an exhaustive sweep like PAW's dequant8 proof), (d) BM x BN = 128x256 for the wide matrices.
   Keep a variant only if the microbench shows a gain >= 10% and the checksum is identical. Ship the best one.
3. Then one kbench row. Expected gemm 2.72 -> ~1.6 s per 21.7K (**est.**; stop and report if the microbench
   cannot beat 90 TOPS).

### P2. Attention (G-X)
Per-launch 39.7 ms (int8) vs 28.9 ms (fp16 KV); the fp16 variant costs 3.15 GiB of VRAM (= 12-13 decode tok/s), so it
is not an option. Closing the gap means the int8 path matching the fp16 loop: PAW's fast dequant took 5 of the 16
ms; the cp.async staging failed in prefill on occupancy (smem 58 KB -> 2 CTAs/SM). Next, by evidence only: (1) read
the SASS of the two instantiations and list the instruction delta per tile; (2) a prefill-only variant that
dequantizes K/V tiles once into registers/fp16 smem shared by the 4-6 query rows a CTA handles; (3) the
per-layer int8/fp16 KV split knob is a placement of VRAM, i.e. a lead/user decision (G-Q), not a kernel item.

### P3. MoE prefill (G-X)
`gate_up` is 11.2 ms/launch avg. TRACKER #42 and PAW's notes already measured the prep->A_gu round trip as
justified (23 vs 36 TFLOPS) and silu is fused: **do not re-open those**. New ground only: the decode cost of the
trellis tiles in the epilogue versus the mma time (microbench with the decode stubbed to measure the mma floor).
If the mma-only floor is within 15% of today, stop: it is at its limit.

### P4. Small-kernel chains (G-X)
~2,900 launches per layer-chunk set, 1.8 s per 21.7K. Fuse by chain, each verified by output checksum:
rmsnorm+quantize+collapse+combine (the hc chain), then conv+delta-rule inputs. Gain **est.** -4.8 s at 150K from
~40% fewer launch/serialization gaps; if the nsys gap time between consecutive kernels is < 1 s per chunk set,
drop P4 (measure the gaps first).

## 2. Decode: 44.4 ms/pass today, 29.3 ms/pass needed

Row 1006_153824 run 2 (K=3, frac 0.2, 175 passes for 512 tokens = **2.93 tokens/pass**, accepted 337 of 434):

| per pass | ms | now what | target |
|---|---:|---|---:|
| ple + hc_mix + hc_mix | 3.7 | small kernels | 3.0 |
| mixer | 7.17 | GDN/DSA at 150K | 5.5 |
| shared | 0.20 | | 0.2 |
| routed MoE | 16.5 | router+publish, plan wait, copy wait (5.3), expert kernel (5.2) | 11 |
| CPU join/combine | 16.8 | waiting on the CPU tier after the GPU side is done | 9.5 |
| **pass** | **44.4** | | **29.3** (= 100 tok/s at 2.93 tokens/pass) |

Facts that bound it (same row): 487.7 cold experts routed per pass = ~930 MB; the CPU tier handles 313.9 slots
(261 distinct experts, ~35 GB/s of DRAM reads = at its floor), PCIe moves 64.6 on demand (125 MB, the 5.3 ms
copy wait) + 78.3 prefetched (154 MB). The link carries ~280 MB in a 44 ms pass = **6.4 of ~21 GB/s: the link is idle
70% of the time**. frac 0.35 (more experts to PCIe) made it worse because it adds *demand* bytes on the critical
path; K=4 made it worse through ring pressure. So the lever is **when** bytes move, not how fast: the CPU tier is a
per-layer serial chain (route -> CPU/copy -> combine, ~0.35 ms CPU wait per layer x 48).

### D0. Pipeline simulator first (the no-trial-error instrument; CPU only, 1-2 days)
`TRUSS_ROUTE_TRACE` (exists, `forward.cu:157`) records every decode layer's routing. Build
`tools/sim/decode_pipeline.py`: per layer, a discrete-event model of {mixer time, router, host plan latency,
copy engine at 21 GB/s with ring slots, CPU tier at its measured per-expert cost, expert kernel, join} driven by the
trace and the residency set. **Calibration gate (must pass before it is used):** reproduce the measured GPU 1 rows
within +-5% and in the right order: K=2 62.7, K=3 67.9 / 61.7, K=4 59.9, frac 0.35 60.5, ADMIT_IDLE=2 61.0, frac 0.2
K=2 baseline. If it does not, fix the model, never the data. Then the sim ranks levers before any engine change.
Questions it must answer with numbers: (a) hints 2 layers ahead instead of 1 (needs a cheaper predictor: use the
tokens' previous-layer residual, measure hit rate offline first); (b) ring slots vs resident experts (VRAM trade
incl. KV lending +1.1 GB); (c) CPU slots moved onto the idle link per layer given the arrival time; (d) start the
CPU tier on the *predicted* misses before the router finishes (speculative CPU start, discard on mispredict:
no numeric change, only wasted work); (e) the best attainable pass with weights untouched.

## 3. Expected outcome (stated plainly)

- **Prefill:** kernel work P1-P4 -> ~2,500-2,600 tok/s; with 370 W ~3,000+. Without the power change 3,000 is not
  reachable by kernels alone (PAW measured the 250 W cap costing ~25-35% of kernel time).
- **Decode:** D2 + the sim-chosen schedule (D0) most likely -> **~75-85 tok/s** with weights and placement quality
  untouched; D1 adds ~5-8; 100 needs D1 + D2 + D3 together or a residency/weights decision from the user.
  I am not promising 100 from schedule work alone.

## 4. Order (one lane at a time on GPU 1; builds -j8; nothing long without a microbench or sim first)

1. P1 steps 1-2 (microbench, GPU 1 only for seconds) and **D0** (CPU only) in parallel. No kbench.
2. By their numbers: ship P1 (G-X + kbench A/B), then D2 profile, P2 SASS study, D1 replay.
3. P4 gap measurement; P3 floor measurement. Build only what the measurement says is > 10% of its kernel.
4. Re-budget after each landed item; stop rules of v1 §6 apply (inside A/B noise after 2 pairs = revert; 3 failed
   attempts on an idea = write why in TRACKER and move on).
5. Anything touching weights, the served config, the power limit or G-Q exceptions: stop, `DECISION` line in
   `data/notify.txt`, wait for the user.

## 5. Rules specific to this plan

- GPU 1 is the serving GPU: `kbench` takes `/tmp/selfopt_gpu2.lock` (name kept, it now guards GPU 1) and stops the brain; use bash `timeout: 1200`
  and wait; a microbench must not hold the GPU more than ~60 s per call (the brain is down meanwhile: batch them).
- No subagents (user rule, limited resources); no `pkill -f` from a shell whose command line holds the pattern.
- Bench noise: decode +-30% under renter load; interleaved A/B (v1 W0.1) before any keep/revert decision on decode.

## 6. Result of the first pass (2026-10-06 17:23) and user decision on power

- **User decision: GPU 1 stays at the 250 W cap** (no `-pl 370`; not wanted for 24 h operation). Every number
  above that assumed 370 W is void; the prefill ceiling at 250 W is ~2,000-2,100 with today's kernels.
- P1 (dense GEMM) FAILED its gate: 69-87 TOPS, issue-bound, no bit-identical variant wins >=10%. P3, P4 dropped
  (measurements within the stop-rule bands). P2: int8 attention is at its fp16x2 floor; only fp16 KV would go
  faster and that is VRAM (a decision). CUDA graphs for decode: ceiling 2.7 ms/pass = +6.4% < 10%, dropped.
- D0 simulator calibrated (<=1.4% error, order matches on six GPU 1 rows): with weights AND placement untouched the
  best attainable decode is **~63 tok/s** (ring slots +1.4, graphs +0.2). The CPU tier is the binding wait
  (~14 ms/pass) and the link is secondary.
- Consequence: **with no power change, no weight change and no placement change, the plan tops out at ~63 decode and
  ~2,000-2,100 prefill.** The only remaining levers are decisions: placement (D1, G-Q gated), MTP re-encode (D3),
  fp16 KV on some layers (VRAM trade), and a larger-throughput CPU/codec change (weights).
