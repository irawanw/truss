# Plan: X3.1 decode 100 tok/s at 150K (and prefill 3,000), for an executing agent (written 2026-10-05)

Written for whoever executes it next (another agent, or PAW-125B X3.1 through the selfopt pipeline). It replaces
trial and error with a budget: every step names the milliseconds it must remove, how that is measured before
building, and the gate that decides keep or revert. The 10-04/05 selfopt session's results and mistakes are in §2.

## 0. Rules (standing user rules; breaking one ends the step)

- **GPU 2 only.** GPUs 0, 1, 3 belong to paying renters. Take `/tmp/selfopt_gpu2.lock` (flock) for any GPU 2 run;
  `kbench` does this. The model server on GPU 2 (pm2 `truss-x31-brain`, :8113) is stopped by every GPU 2 run:
  batch GPU work, never leave it down longer than the run.
- No reboot, sudo, kernel/sysfs/THP changes. RAM is fragmented (no huge pages); renters use 58-77 of 125 GB:
  TRUSS host memory must fit ~40-45 GB. Builds `-j8`.
- Never run from the HDD (`/mnt/hdd`): copy inputs to NVMe first; keep >= 50 GB free on NVMe.
- **No regressions** (user, 10-04): decode and prefill not slower than the best kept row; output tokens EXACT, or,
  for placement-only changes, the quality gate G-Q (§3) passes; **weights, pack, quantization and expert error
  untouched** (no re-encode, re-quantize, prune, skip, approximate). Weight changes are a user decision.
- Speed claims only from 150K-256K runs on real prompts (`eval_clean_150k`, 149,183 tokens), served env.
- The served config (pm2 `truss-x31-brain` / `truss-8113`) changes only after a proposal the user approves.
- Don't fix model behaviour by stripping client context. Commit only when the user asks (agent branches excepted).
- `TRACKER.md` is local-only; add a row per measured result.

## 2. What the 10-04/05 session established (do not redo)

- **Bench noise is ±30% on decode** (36.8-62.6 tok/s for one commit) because renters take CPU time and decode's
  critical path is the CPU tier. Prefill is steadier (±1-2% at load < 30, but 979-2132 under spikes). Single runs
  decide nothing; see W0.1.
- **TRUSS_HINT_K** 3 / 4 vs served 2 (1005_024923, 025943): 4 worse (prefetch 98 -> 214 MB/pass congests the one copy
  stream, wait for copies 10.9 ms); 3 a better profile (pass 40.2 ms) but decode inside noise. Both change tokens.
  Matches TRACKER #85 (X3, 16K: hints 4 86.6 < hints 2 90.2).
- **Wait for copies = demand MB / 13.3 GB/s** at every load (9.95 predicted vs 10.0 measured). Reordering or a
  priority stream cannot recover it; only fewer demand bytes can (W1).
- **PLE:** pipelined next-chunk reads + parallel copy/put: gather 6.77 -> 0.64 s per 150K prefill (kept). Decode PLE
  gather 0.6-2.7 ms/pass tracks page-cache warmth and load, not the change.
- **Expert kernels:** the GPU window kernel (TRACKER #25) and the CPU `gemv_i16` / `gemv_i16f` (#76, #118, 8af5ead)
  are near their floors; CPU frac is op-bound on Zen 2's single vector-multiply pipe. Not a lever without a codec
  change (a weight change: user decision).
- **KL measurement (the session's last result, `selfopt/data/kl/`):** `tk-parity-kl` in decode-step mode (prompt
  half, then 3 tokens a step: the real decode path with ring, CPU tier, dynamic split), 8 x 2048 tokens of
  `eval_clean_150k`, self-reference = the best kept build:

  | run | KL vs self | top-1 | PPL |
  |---|---:|---:|---:|
  | same build, twice | 0.00000 | 100% | 5.2897 |
  | `TRUSS_PCIE_FRAC=0.1` | 0.0858 | 90.96% | 5.3014 |
  | `TRUSS_HINT_K=4` | 0.0835 | 91.09% | 5.2846 |

  The engine is deterministic for a fixed placement; **any** placement change gives KL ~0.085 while perplexity moves
  ±0.2% in both directions. That is router near-tie amplification (a last-bit change flips a top-k choice; TRACKER #53
  saw the same), not lost accuracy. **Consequence: self-reference KL cannot gate placement changes; only KL against
  the true teacher can** (§3 G-Q).
- **Tool fixes made for this (in `selfopt/work/lead`, uncommitted, port to main):** `tools/tk-parity/kl_vs_base.cu`
  now (a) applies the served `TRUSS_*` env (`q::apply_env`), `ple_file`, `prefill_rows`; (b) copies logits on the
  engine stream (a legacy `cudaMemcpy` waits on the doorbell driver's resident work and hangs forever);
  (c) `TRUSS_KL_MAKE_BASE=<tokens.i32>` writes a self-reference base; (d) `TRUSS_KL_TRACE=1` step timing.
- **Process lessons:** (1) A GPU 2 debug loop stops the model server each time: probe with a short capped run that
  prints progress (`TRUSS_KL_TRACE`) before any long run. (2) Never `pkill -f <pattern>` from a shell whose own
  command line contains the pattern (it kills itself, exit 144); kill by PID. (3) `getenv` checks presence:
  remove a variable with `env -u`, not `VAR=`. (4) Section timers (`TRUSS_PROFILE_SECTIONS`) add syncs and change the
  CPU/PCIe split, so tokens: exactness runs must not set it.

## 3. Gates

- **G-X (exact):** greedy tokens of `p0` + `long20k`, 256 each, identical to the reference build (`kbench`). For
  placement-neutral changes (kernels, graphs, host, prefill pipelining).
- **G-Q (quality, for placement-changing changes: residency, hints, splits, admission):** `tk-parity-kl` decode-step
  mode vs the **Q8 teacher logits** `base_chatcode.logits` (llama-perplexity format, 64 x 2048 chatcode tokens; on
  the HDD at `/mnt/hdd/cold_nvme_20260915/kl_code/base/`, 32.5 GB: copy the first 16 chunks' worth to NVMe; check it
  was made with the same tokenizer/vocab 248,320 and model family; if not, regenerate with llama-paw Q8 on GPU 2).
  Pass: KL and top-1 within the noise band of the **baseline build against the same teacher** (measure the band once:
  baseline at 3 placements, e.g. PCIE_FRAC 0.1 / 0.2 / 0.3, gives the spread that placement alone produces), and PPL
  not above the band. Plus one multi-step agent replay (the fix-the-model rule: loops are what users notice).
- **G-S (speed):** W0.1's interleaved A/B; keep only if decode and prefill are not slower beyond the measured noise,
  and the target metric improves beyond it.

## 5. Workstreams, in order

### W0. Infrastructure first (1-2 days; nothing else is decidable without it)

1. **Interleaved A/B bench.** Extend `kbench` with `--ab <ref commit>`: build both, then alternate ref / candidate
   runs (ABAB, 2 pairs minimum) on the 150K prompt, report per-pair deltas and the mean, plus loadavg per run. A
   change is kept when the mean delta beats the pair-to-pair spread. Today's single and `--repeat` rows cannot
   separate a 5% gain from renter load.
2. **G-Q in kbench** (`--quality`): port the §2 tool fixes to main, stage the teacher base on NVMe, add the step that
   runs `tk-parity-kl` on 8-16 chunks and prints KL / top-1 / PPL against the baseline band. Measure the band (§3)
   once and write it into the brief.
3. **Main's startup change (TRACKER #120):** main's working-tree build gave tokens different from 8af5ead at token 4
   in kbench's exactness run (while an earlier `exact.sh` said identical). Find out whether it is the change or the
   reference run's environment (`TRUSS_PROFILE_SECTIONS`, timing-dependent split): run both builds twice each,
   same env, same lock. If the change alters tokens, fix it before committing; then commit and merge into the agent
   branch (cuts kbench's 2 min load to ~8 s, which shortens every server outage).
4. **Merge the agent branch's kept work into main** (user decides when): PLE pipelining/parallel collect, bench
   instrumentation, `--env` in kbench.

### W1. Fewer misses per pass (decode -12 ms; placement change -> G-Q)

Measured in TRACKER #109 / R_REPORT (C2 size, agent traffic, replayed offline): Strata's profile 171 misses/pass, +
our traffic 153, + admission of CPU-computed misses <= 32/pass 109, oracle 88. At X3.1 the hot set is 3,813 experts
(K3.5 experts are larger) and the CPU takes ~337 slots/pass.

1. **Replay before building.** Record routing on the 150K prompt (`TRUSS_ROUTE_TRACE`), replay residency policies
   offline at the real VRAM budget (16.47 GiB for experts at 150K, ring included): today's static profile; profile
   from agent traffic (held-out split); + idle-link admission; + KV lending (E6). Output: misses/pass and CPU slots
   per policy. Pick the policy with the best replayed count; the rest of W1 builds only that.
2. **Usage profile from agent traffic** (`data/usage_strata_rank.f32` today is Strata's): build the profile from the
   served request logs / replays, held-out evaluation. A file change, no code: fastest W1 step.
3. **KV lending** (`TRUSS_KV_LEND`, exists, E6): at 150K the int8 KV caches sized for 262K leave ~1 GB unused;
   replay said +1.1 GB = -10-14% misses. Measure on the A/B bench.
4. **Idle-link admission** (`TRUSS_ADMIT_IDLE`, exists, off: one unexplained hang, TRACKER #113): reproduce the hang
   with a capped probe first (no long runs), fix, then A/B.
5. Gate each with G-Q + G-S; the served-config change is a user proposal.

Expected: CPU slots 337 -> ~200-230, copies -30%: pass -8 to -12 ms.

### W2. Fewer, cheaper device ms outside the experts (decode -5 to -7 ms; G-X)

Plan items E1/E2 (docs/PLAN-20261003 §5d). Today ~2,672 launches per pass.

1. **Profile first:** one nsys trace of 20 decode passes at 150K (`TRUSS_BENCH_PROFRANGE=1`, TRACKER #111 method):
   per-kernel time, gaps, launches. Write the top 10 into TRACKER before changing code.
2. **Wait for host plan 3.3 ms:** the driver thread builds the CPU/PCIe split after routing. Start the plan from the
   pre-gate hints one layer early, or compute the split on the device; the plan must stay the same (G-X).
3. **CUDA graph per window size** (1-5 rows) for the non-expert part of each layer; device-side routing lists.
4. **Fusions:** hc mix + norm + quant; GDN projections + conv + delta rule; router + shared expert in the routing
   bubble.
Gate: G-X; nsys shows the targeted ms gone.

### W3. More tokens per pass (decode +10-15%; MTP weights = user decision)

Served acceptance 327/446 = 0.73 per draft at 150K greedy (2.75 tokens/pass). R5: sampling-side tricks gave nothing;
the draft model must improve. **B6: MTP experts re-encoded at K4-K5 with real Hessians** (and the dense X3.1
encode), plus draft length per window from running acceptance. This changes weights (MTP head only): propose to
the user with the B8 quality gates before starting.

### W4. Prefill 2,130 -> 3,000 (G-X)

1. **Cross-chunk expert-stream pipelining** (PAW's design, in progress on `agent/x31-speed`, uncommitted): stream
   chunk N+1's first layers while chunk N computes its last; one ring, CLOCK with `protect_` for in-flight layers,
   per-layer arrival events; no double staging (VRAM margin 0.75 GB). Est. 70 -> 55-60 s per 150K prompt
   (2,500-2,700 tok/s). Unit-test the ring/protect logic; land in small committed steps.
2. **16K chunks** (today 8K): halves the cold stream per token (36 GB per chunk at 13.3 GB/s = 2.7 s). Check whether
   chunk size changes tokens (attention chunking): if so, it is G-Q, not G-X.
3. **CPU share of few-token cold experts in prefill** (E7 (c), exists for chunks <= 2,048 as `TRUSS_SPLIT_ROWS`):
   extend past 2K with early copies of the next layer's heavy experts (§12i "next").

## 6. Order and stop rules

1. W0.1, W0.2, W0.3 (infrastructure; 1-2 days).
2. W1.1 replay (CPU only, no GPU) in parallel with W4.1 (GPU) and W2.1 (one nsys run).
3. W1.2 -> W1.3 -> W1.4 by replayed value; W2.2 -> W2.3 -> W2.4 by profiled value.
4. W3 after the user approves B6.

Stop rules: a step whose measured gain is inside the A/B noise after 2 pairs is reverted. Three failed attempts on one
idea: write why in TRACKER and move on. Any result that would change weights, the served config, or need a G-Q
exception: stop and ask the user. If W1 + W2 land and the pass is still > 33 ms, re-profile and re-budget before
building more.
