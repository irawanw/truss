# PLAN: DeepSeek-V4.1-Flash-1017 (PAW X3.1 pack) on TRUSS, 2 x 3090 (10-19)

User goal: the keep256 X3.1 pack (73 hot experts/layer at K2.5, K3 in L25-35, 183 cold at K2) served at 256K
context, 70 tok/s decode and 2,000 tok/s prefill with speculative decoding, on GPUs 0 + 2. Pack quality is measured
in `~/ML_projects/dsv41flash/20261018_poc` (TRACKER there); results of this port go to
`~/ML_projects/dsv41flash/20261019_truss_port/`. Reference implementation for the architecture: mmnga/Strata branch

numerical reference: the vendored official model `20261018_poc/scripts/dsref/model.py` (what every KL is measured with).

## What is new vs Flash-Next / LFM (from dsref/model.py)

| piece | DeepSeek-1017 | TRUSS today | work |
|---|---|---|---|
| residual | mHC: 4 copies; per sub-block one fp32 projection [24][4x5120] of the rms-normed stream -> pre (sigmoid), post (2 sigmoid), comb (4x4 softmax + 20 Sinkhorn iterations); the mix a sub-block computes is used by the NEXT one | Flash-Next hc (rank projection + inject): different math | new block `hc_sinkhorn` |
| attention | MQA, 1 KV head of 512 (64 rope, inverse rope on the output), q LoRA 1280, grouped output LoRA (8 groups x 1024), attention sink per head; window ring of 128 raw KV + compressed KV (layers 2-19 ratio 2 with a softmax-gated pooling, 20-39 ratio 1), shared by layer groups (sources 2/8/14/20); indexer (32 heads x 128, top 512) at 2/8/14/20/24/28/32/36, two-level with candidate blocks (2048 x 8) from layer 20; layers 0, 1: window only | DSA (Flash-Next) indexer of blocks of 4: different | new block `attn_ds41` + kernels |
| FFN | sqrtsoftplus router, bias picks / raw score weighs, renorm, x1.5; SwiGLU clamp 10; 1 shared expert (same clamp) | Moe block with RouteFn; window kernel | route fn + `moe::DsV41` shape (**done, #175**) |
| Engram | layers 1 and 14: hash of 2..4-grams over a compressed vocab (8 heads x 3 n-gram sizes = 24 rows of 256 fp8 per token) -> wkv -> gated add to each copy | PLE reader (host rows by thread pool) is the analogue | new block `engram`, host hashing, row reader |

## Storage

Serving needs on NVMe: expert pack ~97 GB, dense Q8_0 ~10 GB *(est.)*, Engram tables 2 x 384M rows x 264 B = ~203 GB
fp8. NVMe free 139 GB (10-19; 491 GB is the renters' docker loop) with the >= 50 GB rule: Engram does not fit as
shipped. Options to measure in P1: rows a code corpus never touches, 4-bit rows, tables on HDD with a RAM row cache.

Budget facts that shape P3-P4:
- **HDD is NTFS through FUSE** (`fuseblk`, mount.ntfs): ~33-51 MB/s under mixed load, so pack builds and loads from
  it are slow; serving loads the expert pack once (~97 GB: ~30+ min at this rate).
- **RAM**: the ExpertStore pins every non-resident expert. Split at layer 20 on GPUs 0 + 2: ~34 GB of experts in
  VRAM (24 GB x 2 - 9.1 GB dense - KV - scratch), ~63 GB pinned; 71 GB available with renters at ~30 GB. No room
  for growth of the cold tier (K2 -> K2.5 would need +17 GB) unless VRAM takes more or experts stream from the file.
- **Decode floor without speculation**: dense weights ~5 GB per token (Q8_0) -> ~6 ms at ~850 GB/s + routed experts
  ~6.5 ms if all hit -> ~80 tok/s ceiling; misses (PCIe / CPU) only lower it. 70 tok/s needs DSpark (block of 5,
  dense reads amortized over the accepted tokens), as mmnga's 60.7 tok/s does.
- **Prefill**: attention ~3.4 GFLOP/token (64 heads x 640 keys x 512) and the indexer O(T^2) at 256K want tensor-core
  kernels (v1 is CUDA-core); grouped wo_a runs as a dense T x 8 projection (8x FLOPs) - replace for prefill.
