# PLAN 2026-10-14: LFM2.5-24B-A2B, PAW X3.1 code-calibrated, on TRUSS

**Ask (user, 2026-10-14):** the same pipeline as PAW-125B-FLASH-NEXT-X3.1 (X3.1 trellis experts, code-262k
calibration, TRUSS engine) on [LiquidAI/LFM2.5-24B-A2B](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B), at four
rates: **2, 2.5, 3, 3.5 bpw**.

**Decisions (user, 2026-10-14):** the bpw is the routed-expert rate, uniform K per pack (dense, conv, attention,
router and embeddings at Q8_0, as in Flash-Next X3.1; whole-model bpw is reported next to it). GPU 2. The
Flash-Next :8113 server and its LCB eval (pm2 12 / 13) were stopped for this, and the X3.1 GGUF shards were moved
to `/mnt/hdd/ml/flashnext/20261003_x31/data/` to make NVMe room (move them back before serving Flash-Next again).

Data, scripts, reports: `~/ML_projects/lfm24b/20261014_x31/`. Rows go in TRACKER.md (prefix `LFM`).

## The model (config.json, HF `lfm2_moe`)

| | |
|---|---|
| layers | 40: 30 short-conv (`conv`), 10 GQA (`full_attention`, layers 2, 6, 10, ..., 38) |
| hidden | 2048; vocab 128,000, tied embeddings, `embedding_norm` (final RMSNorm) |
| attention | 32 q heads, 8 kv heads, head_dim 64, q/k RMSNorm, RoPE theta 1e7, 128K context |
| short conv | `in_proj` 2048 -> 3x2048 (B, C, x), causal depthwise conv L=3 on B*x, out = C * conv, `out_proj` |
| FFN | layers 0-1 dense SwiGLU (11,776); layers 2-39 MoE: 64 experts, top-4, inter 1536 |
| router | sigmoid scores; top-k on score + `expert_bias`; weights = sigmoid scores of the chosen, renormalized |

Routed experts: 38 x 64 x 3 x 2048 x 1536 = 22.95 B weights (96% of the model). Pack sizes *(est.)*:

| K | experts | + Q8 rest (~1.0 B) | whole-model bpw |
|---|---:|---:|---:|
| 2   | 5.74 GB | 6.8 GB  | ~2.27 |
| 2.5 | 7.17 GB | 8.2 GB  | ~2.75 |
| 3   | 8.61 GB | 9.7 GB  | ~3.23 |
| 3.5 | 10.0 GB | 11.1 GB | ~3.71 |

**Every pack fits in one 3090 with room for KV** (10 attention layers x 8 x 64 x 2 x 2 B = 20 KB/token: 128K ctx =
2.6 GB). So the Flash-Next residency machinery (CPU tier, PCIe streaming, doorbell, usage ranks) is not needed: all
experts live in VRAM. LFM has no MTP head, so there is no built-in spec decode.

## Phases and gates

| | What | Gate |
|---|---|---|
| C0 | Code-262k corpus re-tokenized for LFM (`c0_retokenize.py`) | DONE: 249 x 1024 train, 249 x 1024 held-out (first 32 used), ChatML framing kept |
| C1 | bf16 download (48 GB, NVMe), Q8_0 GGUF by llama-paw `convert_hf_to_gguf` | llama-paw runs it; PPL on held-out code sane |
| C2 | Capture: MoE input rows + routes per layer on the corpus, HF bf16 streamed layer by layer on GPU 2 (`c2_capture.py`, port of `b1_capture.py`) | row counts per expert; no expert < 1,000 rows (64 experts top-4: ~16K/expert *(est.)*) |
| C3 | X3.1 encode, 4 rates (`b1_encode.py` port: exllamav3 1.5.1 scale refit + LDLQ drift, per-expert Hessians, prior from layer Hessian) | held-out output error per K monotone; matches Flash-Next per-K error within 2x |
| C4 | Pack: one GGUF per rate (Q8_0 rest + `m3_{trellis,meta,suh,svh}` experts) | byte counts = table above |
| C5 | Quality before TRUSS: llama-paw `lfm2moe` with X3 MoE (port of qwen4exp's X3 wiring) | KL vs bf16 per K; HumanEval/LCB-lite per K |
| C6 | TRUSS port on the engine split (docs/ENGINE.md, TRACKER #160): `src/model/lfm2moe/` (config, binding, composition) + new blocks only for new layer kinds - see the C6 list below | layer parity vs llama-paw rel err <= 1e-3; full-model KL = llama-paw's; **no edits in engine/, api/, server/** |
| C7 | Serve + bench | PP and TG >= llama-paw at equal KL, per K |

Kill rules: C3 error at K2 worse than 2x Flash-Next K2 on the same metric -> stop and look at the Hessians before
encoding the other rates. C6 slower than llama-paw on the same pack after the kernel pass -> report, don't ship.

## C6: what the LFM port adds (2026-10-14, after the engine split)

Everything else (slots, verify windows, checkpoints, layer split, expert residency, C API, server) is the engine's.

| piece | where | note |
|---|---|---|
